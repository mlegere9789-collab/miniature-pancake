# --- Huge-scale box (1e6-unit coordinates) with an otherwise perfectly
# ordinary radius (2, on a 10-unit box - identical proportions to
# fillet_script.txt's own working case, just translated far from the
# origin). This USED TO BE known infeasible at this coordinate magnitude
# for the reason adversarial_corpus_notes.md still documents in full
# (dino8::kernel::Mesh stores vertices as single-precision ON_3fPoint
# floats, and 1e6 * 2^-23 ~= 0.12 units of quantization swamps a 2-unit
# fillet feature once the result is tessellated), and the old generic
# BuildFillet path - built from independently numerically-intersected
# spine samples, then validated by tessellating and checking closure -
# still hits exactly that gap and still fails gracefully the same way.
# **This pass:** the new TryExactFillet path (see cmd_fillet.cpp) reaches
# this case FIRST now, and it does not fail - kernel::FilletConvexEdge
# builds the whole result as ONE coherent double-precision Brep sharing
# literal vertex positions across every trim, rather than stitching
# together independently-computed offset-surface-intersection samples, so
# a later float-mesh tessellation for Volume quantizes every shared vertex
# the SAME way instead of drifting the two sides of a seam apart - no gap
# ever opens. Verified, not assumed: Volume below comes back 991.4, the
# same exact closed-form value fillet_script.txt's own origin-scale
# Radius=2 box case already verifies, not 0/"not closed". Still
# genuinely infeasible for whatever falls through to the old approximate
# path (a curved adjacent face, Radii=, or any other PlanarFaces()
# rejection) - see adversarial_corpus_notes.md's own updated note.
Box 1000000,0,0 1000010,10,0 10
FilletEdge
Radius=2
1000010,10,5
Enter
SelAll
Volume
@expect_objects 1
