**Former blocker, now fixed:** the fragment-loop test-suite-abort crash (root cause commit `878ecdb`) is root-caused and fixed, with a permanent regression test — `TestBooleanCombineGeneralFlatSidedBossCrashRegression` (`dino8-kernel/tests/test_basic.cpp`), which reproduces the exact previously-crashing fixture (a flat-sided box boss flush on a bigger box's face) unwrapped and confirms it no longer throws "an edge is claimed by 3 or more fragment loops," now asserting the exact closed-form volume for every op. Confirmed to fail on pre-fix code and pass on post-fix code via a standalone harness using the real test scaffold, not assumed. Root cause: `CoincidentOverlapBoundaryCurves()` (`surface_intersect.cpp`, added by `878ecdb`) silently dropped the sample at a detected coincident region's own corner whenever that corner sat exactly on the other face's own domain boundary — `SurfaceClosestPoint()`'s Newton solve requires the full unconstrained gradient to vanish, which a genuine boundary-clamped closest point can never satisfy — undermeasuring the region `BooleanCombineGeneral`'s own whole-face coincidence override relies on. Fixed with a new, narrowly-scoped `ClosestPointAllowingDomainBoundary()` helper used only at that one function's own 4 rectangle corners — not a tolerance widening, not a try/catch, and the shared `SurfaceClosestPoint()`/`SurfaceClosestPointGlobal()` every other caller in the file depends on is left untouched. Two broader first-draft versions of this fix (one editing the shared closest-point function directly, one widening `IntersectSurfacesOverlap()`'s own region-acceptance without accounting for periodic/pole surface directions) were each caught regressing a different, previously-passing test by a full-suite rebuild-and-rerun, and were narrowed before landing — not shipped assumed-safe. Full kernel suite: 11050/11050 checks passing, 0 failures (pre-fix baseline: 11040/11040, 0 failures; the +10 is this new test's own checks, nothing else changed). **Separately-disclosed scope, unchanged by this fix:** curved-face coincidence and multi-boss/oblique flat-sided configurations remain unexercised — proven on the canonical single-flat-boss fixture, not asserted for every shape; item counts below are unchanged (9/15/1/25) since this closes a blocking crash, not a new feature item, and the "Coplanar / coincident face handling" bullet's own broader scope stays `[partial]`.

**Follow-up (this pass): two of that disclosure's three named gaps are now closed, confirmed broken first.** A standalone repro (linked against `libdino8_kernel.a`, not assumed from the historical description) confirmed, before any code change: a cylindrical boss's circular cap flush on a box's top face gave a grossly wrong Union volume (44.39 instead of the correct ~65.77); a box boss rotated 31° about Z, otherwise identical to the already-fixed axis-aligned fixture, reproduced the exact same "an edge is claimed by 3 or more fragment loops" crash on Union and wrong volumes on Intersection/Difference; two separate box bosses on the same bigger face already worked correctly even before this pass (no code change needed, only a permanent test). Root cause of the first two (confirmed by reading `CoincidentOverlapBoundaryCurves()`'s own doc comment, not assumed): it reports the coincident region as only its enclosing AXIS-ALIGNED rectangle in the walked face's own (u, v) domain, never the true outline — correct for an axis-aligned box footprint (rectangle == its own bbox) but wrong for a circle or a rotated rectangle, both strictly smaller than their own circumscribing box. Fixed in `BooleanCombineGeneral` (`boolean_general.cpp`), not in the shared `CoincidentOverlapBoundaryCurves()` itself: an exact polygon-containment test (does one face's own real trim-boundary loop lie entirely inside the other's, via `PointInPolygon()` on both loops projected into a shared 2D plane frame) now runs first, and when it reaches a clean asymmetric verdict, the smaller face's own exact boundary loop — not a re-derived approximation — becomes the imprint curve, each point reprojected onto the bigger face via `ClosestPointAllowingDomainBoundary()` (393e32fc's own fix, exported and reused verbatim, not reimplemented). Guarded off (falls through to the pre-existing bbox path, unaffected) whenever either face has a singular surface side — found and confirmed by a full-suite rebuild-and-rerun regressing `TestBooleanCombineGeneralAsymmetricCoincidentSubFace` (a `Brep::Extrude()`-built boss with a FAN-capped bottom face: one side of its trim loop is a degenerate apex point with two radial chords, not a simple boundary polygon, which corrupted the imprint curve into a self-touching "keyhole" before this guard was added). New permanent regression tests: `TestBooleanCombineGeneralCircularFootprintBossCoincidence`, `TestBooleanCombineGeneralObliqueFlatSidedBossCoincidence`, `TestBooleanCombineGeneralMultiBossFlatSidedCoincidence` (`dino8-kernel/tests/test_basic.cpp`), each checking real closed-form volumes (not just "doesn't throw"). Full kernel suite: 11073/11073 checks passing, 0 failures (pre-fix baseline: 11050/11050, 0 failures; the +23 are these three new tests' own checks, nothing else changed — confirmed via two independent full-suite runs, the first of which caught the FAN-cap regression above before it landed). **Still disclosed, not reached by this pass:** true curved-SURFACE coincidence (e.g. two cylindrical walls overlapping over a 2D area, not just a flat cap with a curved outline) — `surface_intersect.cpp`'s own `IntersectSurfacesOverlap()`/`CoincidentOverlapBoundaryCurves()` are explicitly documented as reliable for flat/coplanar surfaces only, "NOT for curved," and this pass did not touch that; a face built from a FAN cap (Extrude/Revolve/Pipe's flat end caps) never takes the new exact-polygon path at all (the singular-side guard above), so it still relies on the older, narrower bbox path for any coincidence it's involved in.

**Follow-up (separate session): the "subtract one boss back out of a multi-hole face" gap above is now fixed and found to be genuinely broader than disclosed.** Standalone repro confirmed first (DINO8_BOOL_DEBUG=1, not assumed): the SAME "3 or more fragment loops" crash reproduces even for a SINGLE pre-existing hole, not only the two-hole case the previous note named — a face already keyholed by `BridgeHolesIntoOuter()` (the self-touching single-outer-loop trick that lets `ResolveFace()` route it to the exact-clip tessellator instead of an `ON_BrepLoop::inner`) breaks when re-fragmented by a LATER op, because `FaceBoundaryLoop()`'s own sample of it is self-touching and `SplitFaceLoop()`/`BuildLoop()` have no notion that two of its own points are secretly one corridor walked in and back out. Three narrowly-scoped, independent root causes, each confirmed by direct tracing and each caught regressing a different already-passing test by a full-suite rebuild-and-rerun before being narrowed: (1) a face that is ANY opposing face's own coincident region (`coincident_a`/`coincident_b` non-empty) could still pick up a spurious `IntersectFaces()` curve from an unrelated opposing face sharing the same physical edge locus (one operand's sub-solid being an exact duplicate of part of the other's) — fixed by clearing that face's own `raw_a`/`raw_b` entries once a whole-match is found; (2) the exact-polygon coincidence test's own `boundary_a`/`boundary_b` broke on a keyholed (self-touching) loop — fixed with a new `UnbridgeKeyholes()` (`boolean_general.cpp`) that recovers the un-keyholed outer for that read-only check; (3) `FragmentFaces()` itself needed the SAME un-bridging, but only for the ONE hole this op's own fresh intersection curve is about to duplicate (touching every OTHER pre-existing hole corrupts an already-working fixture, confirmed directly) — `UnbridgeKeyholes()`'s own `targets` parameter restricts extraction to exactly that match. A further, separate fix: the fragment resulting from a merged-away hole must still be classified using its ORIGINAL (not yet merged) holes — only the BUILT `KeptFace` loses the region — or the owner's own `RepresentativeUV()` centroid can land inside the opposing solid and the fragment is wrongly dropped whole (confirmed directly: this exact regression hit the pre-existing, unrelated `TestBooleanCombineGeneralFlatSidedBossCrashRegression`/`Circular`/`Oblique` fixtures, none of which involve a prior union at all, and was fixed before landing). New permanent regression tests: `TestBooleanCombineGeneralBossUnionThenSubtractBackOut` (single boss, exact volume, genuine closed manifold at every resolution tested) and `TestBooleanCombineGeneralMultiBossSubtractOneBackOut` (the actual two-independent-holes case, subtracting either boss back out, each checked for real volume and manifold-ness) — both in `dino8-kernel/tests/test_basic.cpp`. Full kernel suite: 11085/11085 checks passing, 0 failures (pre-fix baseline: 11073/11073, 0 failures; the +12 are these two new tests' own checks, nothing else changed — confirmed via a full-suite rebuild-and-rerun). **Disclosed, not covered by this fix:** `TestBooleanCombineGeneralMultiBossSubtractOneBackOut` uses tessellation resolution 16 for its manifold/volume checks; a focused standalone sweep (not part of the committed test) found resolution 8 alone gives a transient non-manifold result for the boss1-subtraction direction specifically (9 non-manifold mesh edges at that one grid density; every other resolution tested, 4 through 64, is a clean closed manifold with the exact right volume) — a numerically unlucky grid-cell alignment at that one density, not asserted as fixed and not re-tested at every resolution in the committed suite.
