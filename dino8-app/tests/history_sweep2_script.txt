# History / UpdateHistory extended to Sweep2 (Sweep2Command, cmd_surface.cpp;
# RebuildSweep2, history_rebuild.h), single-cross-section case only: the same
# source-curve-moves -> UpdateHistory-rederives loop history_script.txt,
# history_pipe_script.txt and history_sweep1_script.txt already prove for
# Extrude/Revolve/Loft/SubDLoft/Pipe/Sweep1, now for Sweep2 as an eighth
# tracked command - see cmd_history.cpp's own header comment for the full
# scope list. The money check is a real bounding-box move, not just an
# object count, so a fake/no-op rebuild would fail this the same way it
# would in the other history_*_script.txt files.
#
# Two parallel vertical rails (5 units apart in X) and a single circular
# cross section at rail1's own start point. Both rails are straight and the
# same length, so the rail-to-rail width is constant along the whole sweep -
# the same "no net scaling" case history_sweep1_script.txt's own single
# straight rail is, which is why the swept tube's bounding box below comes
# out identical to that file's own. As with Sweep1, RebuildSweep2 anchors the
# section where it sits along the rails (the surface covers the rails and
# passes through the section wherever it is), so the two edits below test two
# different things: sliding the section ALONG the rails (+5 in Z) must leave
# the surface covering the rails' own z=0..10 extent (it used to shift the
# whole tube to z=5..15 - the kernel's Brep::Sweep2 carries the section
# rigidly from the rails' START frame, which was the defect); moving it
# SIDEWAYS (+3 in X) is then the edit that proves UpdateHistory genuinely
# re-derives the geometry, since it changes the swept bounding box in X. See
# history_sweep1_script.txt's header comment.
#
# Object ids below are the deterministic 1-based counter Document::Add
# assigns, in creation order.
