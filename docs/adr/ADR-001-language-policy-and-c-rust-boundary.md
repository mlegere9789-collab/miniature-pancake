## 1. Context

The plan (5.1) directs that new core systems are written in Rust while the existing C++ kernel
(about 129,000 lines on openNURBS) and application (about 135,000 lines) are extended in place. The two
meet at one narrow C ABI (5.2). The plan estimated two to three days for a first working boundary and made
Spike R1 the measurement. The gate in 5.2 has two parts: (1) one command round-trips through the log
with overhead under 1 ms, and (2) the full application test suite still passes.

## 2. Decision

1. Language policy as in plan 5.1 stands: Rust for the operation log, snapshots and merge, the
   incremental engine and scheduler, the entity store and query engine, the sync server, the open
   container format; C++ for the kernel, the application, commands, the GL viewport and the UI.
2. The boundary is a plain C ABI generated by cbindgen into one committed header. No C++ type crosses it.
   Calls are coarse (per command, per query, per batch), never per vertex or per face.
3. Every function that can fail returns an `int32_t` status (`D8_OK` = 0, codes are `#define` constants, not
   an enum) and takes an optional caller-owned `D8Error*` (code, detail, message of at most 239 UTF-8 bytes).
   No thread-local "last error".
4. Handles are 64-bit tokens (32-bit generation, 32-bit slot, zero never valid) into a table of `Arc`
   objects. A closed, copied, forged or zero handle answers `D8_ERR_BAD_HANDLE`, never undefined behaviour.
   `d8_*_close` zeroes the caller's variable.
5. Ownership: each side frees only what it allocated. Rust never hands memory to C++ to free (no `d8_free`).
   Variable-size output uses a two-step protocol (`D8_ERR_BUFFER_TOO_SMALL` plus true sizes, caller retries).
   Inputs are borrowed for the duration of the call.
6. Panics never cross: every `extern "C"` body runs in `catch_unwind` and becomes `D8_ERR_PANIC` plus message.
   The release profile keeps `panic = "unwind"`. A panic while a log lock is held poisons that log only.
7. Callbacks from Rust into C++ are typed `extern "C-unwind"`; every C++ function given to Rust is a thin wrapper
   with `try { ... } catch (...) { return <error code>; }`. A C++ exception that escapes anyway aborts the
   process (proven) instead of unwinding through Rust frames. The library never calls a callback while holding
   one of its locks.
8. Exactly one Rust staticlib per final binary: a single facade crate that depends on the component crates
   and is the only crate exporting `extern "C"` functions and the only one allowed `unsafe`.
9. `d8_abi_version()` is checked against `D8_ABI_VERSION` at start-up; struct sizes and the error-message
   offset are pinned by compile-time assertions on both sides.
10. CMake drives Cargo through Corrosion (v0.6.1 tested); the generated header is committed and CI fails on drift.
11. Durability policy for the log (see ADR-002): the "append under 1 ms" target is read as a write-through
    append; power-loss durability is a group commit or timer, not a per-append `fdatasync`.

## 3. Measured evidence

Run conditions: 4-vCPU Intel Xeon 2.30 GHz VM shared with about 20 other agents (load average 6 to 13
during these runs), Ubuntu 24.04, GCC 13.3, rustc/cargo 1.97.0, CMake 3.28.3, Ninja. C++ program built
`RelWithDebInfo` (-O2); crate in the `release` profile (opt-level 3, thin LTO). Record: 48-byte header + 64-byte
parameters + 2 input ids + 1 output id = 160 bytes (168 in the file). Shown as median [min to max] over 7
complete runs of the program unless noted. Source: R1 section 4.

| Measurement (1,000,000 operations, static link) | Microseconds per call |
|---|---|
| Bare C-to-Rust call, no guard | 0.0005 [0.0005 to 0.0013] |
| Guarded call (panic catch + error record), does nothing | 0.0011 [0.0008 to 0.0027] |
| Handle lookup + lock-free length | 0.0315 [0.027 to 0.038] |
| `d8_log_append`, mean | **0.175 [0.142 to 0.200]** (best single run 0.113) |
| Same append called natively from Rust, no boundary (5 runs, different minutes) | 0.119 [0.099 to 0.128] |
| `d8_log_append_batch`, 1,000 per call, per operation | 0.118 [0.107 to 0.187] |
| `d8_log_read`, sequential, per record | 0.079 [0.067 to 0.193] |
| 4 threads, one shared log, per append (aggregate) | 0.165 [0.148 to 0.288] |
| Dynamic link (cdylib), `d8_log_append` mean (3 runs) | 0.152 [0.119 to 0.195] |

Tail latency (every one of 1,000,000 calls timed, 7 runs): p50 0.079 us, p99 1.48 us [1.40 to 1.61],
p99.9 2.71 us [2.52 to 2.99]; worst single call 4,049 to 19,011 us (median 7,945); calls over 1 ms per million: 14
[4 to 38]. The worst calls are the host, not the library: 5,000,000 timed calls of an EMPTY guarded function show
worst 4,043 to 7,856 us and a median of 13 calls over 1 ms per run, and a library-free page-touching loop (scratch
program, not committed) shows the same. A run where the process was descheduled for about a second (mean 1.2
us) is excluded from the table.

Durability modes of the file-backed log (R1 4.3):

| Mode | Microseconds per append | Survives |
|---|---|---|
| In memory only | 0.175 | nothing |
| File, buffered (64 KiB, flushed on sync and close) | 0.66 [0.61 to 0.85] | clean exit |
| File, write-through (one `write` per append) | 1.05 [0.91 to 1.14] | process crash |
| File, `fdatasync` per append | 900 to 3,795 (5 runs); 2,300 to 5,778 (two earlier runs) | power failure |
| One `fdatasync` after 200,000 buffered appends (32 MiB) | 51 to 124 ms in total | power failure |

Verification (final code): C++ program 1,180 checks, 0 failures (10 runs); ASan+UBSan through CMake `ctest` 3 of
3 pass, 1,181 checks per run, 0 diagnostics; TSan on the C++ side with Rust frames suppressed: 0 reports;
deliberate panic (3 payload kinds) returns `D8_ERR_PANIC`, handle stays usable; unguarded panic in a forked child
exits by signal 6; C++ exception escaping a `C-unwind` callback exits by signal 6; stale, closed, zero and forged
handles and NULL, misaligned, oversized arguments answer status codes; file recovery cut at every byte of the
last frame, one flipped byte and a foreign file lose at most the damaged tail; `cargo test` 39 tests pass
(20 unit, 4 concurrent, 9 C-ABI, 6 recovery); loom 3 models (293 + 46 + 4 interleavings, plus a negative control
that is found); clippy 0 warnings; fmt and header-drift checks clean. Build: CMake configure 1.9 s, cold build 6.8
s, 89 MB build directory. A stripped C++ hello program is 14 KB, with the Rust log linked 349 KB.

Re-stated gate proposal (for the owner to approve, replaces the wording "log append under 1 ms"):
"A log append that is on disk through the operating system (write-through, survives an application crash) costs under 1 ms
at p99 (R1 measured only the 1.05 us mean for write-through; Spike B measured wall p99 of 62.5 to 140.9 us for its memory, WAL and background-fdatasync policies, ADR-002); power-loss durability is a group commit or timer with a documented loss window (default
at most 20 ms, ADR-002); per-append `fdatasync` is opt-in and its time is reported on the owner's hardware with no
pass or fail until it has been measured there."

## 5. Consequences

- Positive: the boundary is cheap (the handle lookup is the only boundary-specific cost, about 0.03 us), its
  failure modes are known and contained, and the rules are written down and tested.
- One facade staticlib (F3: two Rust staticlibs in one program gave 208 "multiple definition" errors with GNU ld,
  20 with lld) forces all Rust components to be rlib crates behind one `d8-ffi` crate; the ABI of the log, the store
  and the engine share one status namespace and one handle table design.
- Hot-path containers in the real core must not be plain `Vec` growth (F4: the first 1M run showed slow appends at
  sequence numbers 131,072, 262,144 and 524,288 of 0.5, 1.2 and 2.1 ms, removed by a paged sequence). The timed
  pass in the probe is how to catch it.
- Header hygiene (F7): constants carry a `D8_` prefix, internal ones are `cbindgen:ignore`.
- The app needs a C++ wrapper layer: an RAII class per handle type, a `catch (...)` template for callbacks, a
  status-to-result adapter.

## 6. Risks

- Gate part 2 (app suite) is untested; an integration surprise in the app CMake is possible.
- The log in the probe is single-process; two processes appending to one file would corrupt it (a file lock is needed).
- The handle table is one global lock; fine for coarse calls, not for per-vertex calls (which the rules forbid).
- Worst-case latency was measured on a heavily shared VM and is dominated by the host; quote no worst case before re-measuring on owner hardware.
- Rust-side soundness rests on loom and the type system until Miri and a Rust TSan job exist.
- Callback typing `C-unwind` relies on stable Rust behaviour for foreign exceptions (abort, not unwind through Rust); this is observed on rustc 1.97.0 only.
- The probe-only `d8_probe_*` functions must be gated behind a Cargo feature before shipping.
- Record parameters are opaque bytes; growing the ABI to about 1,070 commands' worth of typed parameters is the largest remaining piece (ADR-002, Stage 2).
