- `Brep::MergeCoplanarFaces()` walks this Brep's own `ON_Brep` edge/face adjacency directly (never through the Manifold mesh-boolean engine, which — being mesh-only — genuinely cannot represent the non-manifold topology the old note complained about) to weld adjacent, coplanar faces sharing a manifold-safe (exactly two trims) edge into one bigger face. `NonmanifoldMerge` (`cmd_solidtools.cpp`) now joins the selection like `Join` and then runs this, instead of falling back to a plain `Join` with no merge at all.
- `Brep::ReplaceEdgeCurve()` re-projects every affected face's own trim onto a substitute 3D curve via closest-point projection (the same technique `SplitFace`/`SplitEdge` already use to re-derive a trim after a topology edit), replaces the edge's own 3D curve, and throws a specific exception (`std::invalid_argument` for a mismatched endpoint, `std::runtime_error` for a substitute that strays off a face's own surface) rather than silently building invalid geometry. `ReplaceEdge` (`cmd_srfedit.cpp`) now calls it instead of printing a "planned" note.
- `Brep::UnjoinEdge()` duplicates a shared edge's own 3D curve into a second `ON_BrepEdge` and re-points one of its two trims onto it via `ON_BrepTrim::AttachToEdge()`, splitting one shared (2-trim) edge into two naked (1-trim) edges while keeping both faces in the same polysurface — Rhino's own `UnjoinEdge` semantics, not `ExtractSrf`'s separate-object workaround. `UnjoinEdge` (`cmd_srfedit.cpp`) now calls it.

A genuine, checked-directly correctness bug surfaced and was fixed while building `MergeCoplanarFaces()`/`ReplaceEdgeCurve()`: this class's own per-face side tables (`face_trim_loops_` and five parallel siblings — an `exact_clip`/arc-run/notch fast path `ResolveFace()`, in `brep.cpp`, prefers over deriving a face's trim from its real `ON_Brep` topology) have no way to track a face being deleted, appended, or renumbered by direct `ON_Brep` mutation, so without an explicit fix a later `Tessellate()` silently read a stale, pre-edit trim polygon for whatever face ended up at a given index — corrupting that face's own shape (and, through it, a whole solid's divergence-theorem volume) while every topological check (`IsValid()`/`IsManifold()`/`IsSolid()`) still passed, since none of those read this class's own side tables. Both new methods now clear the side tables outright after mutating the raw `ON_Brep` (an intentionally blunt but always-correct fix — see `MergeCoplanarFaces()`'s own doc comment in `brep.h` for the full reasoning and its one disclosed, narrow cost: another curved face's own verbatim fast-path record elsewhere in the same `Brep` falls back to the slower, still-correct generic path too).

New regression tests: `dino8-kernel/tests/test_basic.cpp` gained `TestMergeCoplanarFacesWeldsTwoAdjacentSquaresIntoOne`, `TestMergeCoplanarFacesRestoresBoxAfterSplittingFourFacesAtOnePlane` (face count, `IsValid`/`IsManifold`/`IsSolid`, and volume before/after — this is the test that caught the stale-side-table bug above), `TestReplaceEdgeCurveRefitsANakedEdgeToABowedSubstitute` (including a `PlanarFaces()`-based check that the *tessellation pipeline*, not just the raw edge object, reflects the new curve), `TestReplaceEdgeCurveThrowsOnEndpointMismatch`, `TestReplaceEdgeCurveThrowsOnSurfaceMismatch`, and `TestUnjoinEdgeSplitsSharedEdgeIntoTwoNakedCopies` (naked-edge count via the same `TrimCount()==1` test `ShowEdges`/`RemoveAllNakedMicroEdges` already use). **Update (2026-09-21, CreateRegions pass):** `CreateRegions` is fixed to `Implemented`. Its old note read "Every region of up to 6 overlapping closed curves; open-curve networks are planned" - the gap was that `Regions()` (`cmd_solidtools.cpp`, the shared helper behind `CreateRegions`/`CurveBoolean`/`PlanarUnion`/`PlanarDifference`) rejected any selected curve that was not itself `ON_Curve::IsClosed()`, so a network built from open curves meeting end-to-end never got as far as the existing overlapping-closed-curve boolean logic at all. The fix (`ChainOpenCurvesIntoLoops`, same file) treats every open curve's two endpoints as a planar graph's vertices (points within `10x` the document tolerance are the same vertex) and the curve itself as an edge, groups them into connected components via union-find, and - for exactly the components where every vertex has degree 2, the standard graph fact that pins such a component down as a single unambiguous cycle - walks that cycle into one closed, endpoint-snapped boundary (`ON_Curve::SetStartPoint()`/`SetEndPoint()` remove the sub-tolerance seam gaps a naive concatenation would leave). Each such assembled loop is then handed to `ON_BrepTrimmedPlane`'s own multi-curve-boundary overload (`RegionSlabFromBoundary`, refactored out of the pre-existing single-curve `RegionSlab` so both share the same mesh/extrude tail) exactly like a single already-closed input curve was before, so it participates in the existing up-to-6-region overlap/subset boolean logic unchanged. A component with a degree-1 vertex (a dangling end) or a degree-3+ vertex (a branch point - three or more curve-ends meeting at one point, e.g. a "Y", which admits more than one possible face) is deliberately left unresolved rather than guessed at, with an explicit warning naming how many curves were skipped and why; full planar-subdivision arrangement (picking one face out of several a branching network could bound) remains real future work, honestly noted in the command's own registration text rather than implied as covered. The working plane for an open-curve-only selection is derived from the *assembled* loop's own overall shape (its pieces joined into one `ON_PolyCurve` first), not from any single input curve's own individually-reported plane - `ON_Curve::IsPlanar()` on one straight line alone reports some plane containing it, not necessarily the plane the rest of the network actually lies in, and a first draft of this fix got exactly that wrong before the triangle test below caught it.

Verified with three new `tests/solidtools_script.txt` cases (`smoke.sh`'s `stcheck` family): (1) three open `Line` segments meeting end-to-end into a right triangle (legs 30 and 40) - `CreateRegions` reports "regions of 1 region(s) -> 1 closed curve(s)", and the result, turned into a real trimmed-plane surface via `PlanarSrf` and measured with `Area`, reads exactly 600 = 0.5×30×40 (an exact match, not approximate, since every edge is straight so the mesher adds no extra vertices); (2) a mix of an assembled open-curve loop (an `Arc` + a `Line` closing its diameter into a semicircle, r=10) and a separate, untouched closed `Circle` (r=5) - `CreateRegions` reports "regions of 2 region(s) -> 2 closed curve(s)" and the semicircle region's own measured area (153.1) is within this shared `Regions()`/`Outlines()` pipeline's own pre-existing chord-tolerance faceting error of the analytic 0.5×π×10² = 157.08 (that gap, ~2.5%, comes from the mesh tolerance scaling off the *whole selection's* bounding box - including the far-away circle - a pre-existing characteristic of this shared pipeline, not something the open-curve-loop fix introduced); (3) a negative case - three open `Line`s meeting at one shared point (a branch/"Y", not a loop) - produces the expected "3 open curve(s) don't close into a simple loop (a dangling end, or 3+ curve ends meeting at one point) and were skipped" warning and no regions, confirming the honestly-scoped limitation surfaces as a clear message rather than a silent no-op, a wrong guess, or a crash. Full `xvfb-run tests/smoke.sh` run green (0 real FAIL) after this change, including the pre-existing `CurveBoolean`/`PlanarUnion`/`PlanarDifference` cases (which share the same `Regions()` helper and are unaffected for already-closed-curve input). **Update (2026-09-21, Hydrostatics pass):** `Hydrostatics`'s own blocking-capability row below ("A trim/heel hydrostatic solver") is now closed - fixed to `Implemented`. Its old note read "Volume, displacement, and center of buoyancy are computed for real ...; longitudinal/vertical prismatic coefficients and a trim/heel solver are not implemented." Both gaps are now real, from-scratch numeric algorithms over the actual clipped mesh, not hardcoded constants: (1) longitudinal prismatic coefficient Cp = displaced volume / (waterline length x max transverse section area) and vertical prismatic coefficient Cvp = displaced volume / (draft x waterplane area). The waterline length is the extent, along whichever construction-plane axis the hull spans further (its own long axis), of the waterplane outline already being sliced for the existing waterplane-area number; the max section area is found by slicing the *whole* hull (not just the already-submerged triangles) at 60 stations along that axis (`drafting::SliceMeshToChains`, the same helper the waterplane calc already uses), clipping each station's closed outline loop to the half below the waterplane with the identical edge-crossing technique the volume clip already uses (generalized from a triangle to an n-gon), and taking the largest resulting area; draft is the deepest mesh vertex below the waterplane. (2) A real 2-unknown damped Gauss-Newton trim/heel solve (`kernel::NewtonSolve`, the same solver `SphereTangentToThreeSurfaces` already uses) that re-clips the mesh at each trial waterplane orientation and drives to zero the in-plane (u, v) offset between the center of buoyancy and the object's own geometric centroid (the assumed center of gravity, documented in the registration text and the code's own comment as the chosen convention, since this app carries no separate mass/density model and Rhino's own solver's exact convention isn't available to check against) once both are projected onto the trial waterplane along its own normal. Trim rotates the trial waterplane about the construction plane's transverse (Y) axis, heel then rotates it about the construction plane's original (unrotated) longitudinal (X) axis, both applied about the point on the *base* waterplane directly under the hull's own centroid (not the construction plane's own origin, which for a hull modeled away from the world origin would put the whole hull on the end of a large lever arm and swing it out of the water for a trial angle of only a few degrees - a real bug caught and fixed during this pass's own verification, not shipped).

**Update (2026-09-21, Sketch pass):** `Sketch`'s own blocking-capability row below ("Continuous mouse-drag capture in the command engine") is now closed - fixed to `Implemented`. **Update (2026-09-21, PackSubDFaces pass):** `PackSubDFaces`, previously listed here, is also removed — fixed to `Implemented`. It now builds a real UV-atlas layout for a SubD's current control-net faces instead of reporting only the face count: `UnwrapFacesLocally` (`cmd_subd.cpp`) gives each control-net face its own independent planar (box) unwrap via that face's own Newell-method normal (`Net::FaceNormal`, already used elsewhere in this file) and an orthonormal local (u, v) basis built from it, so every face keeps its true aspect ratio (a planar face, e.g. any face of a SubD box, unwraps with zero distortion). `ShelfPackFaces` then packs those per-face rectangles - each padded with a 12%-of-size gutter so packed islands never touch - into the unit square via a real shelf (Next-Fit Decreasing Height) bin-packing algorithm: rectangles sorted by height, placed left-to-right into shelves of a bin whose width is chosen by the standard "aim for a roughly square strip" heuristic (`sqrt(total allocated area)`, clamped up to the widest single cell) rather than the widest-cell-only width an earlier version of this function used (which forced exactly one rectangle per shelf whenever most faces were a similar size, e.g. a cube's 6 equal faces, wasting most of the unit square - caught and fixed during this pass's own verification, not shipped). The whole shelf layout is then rescaled by one single uniform factor (never a per-axis stretch, so no face's own aspect ratio is distorted) so it fits exactly within [0,1]x[0,1]. Each face is packed as its own independent island - no adjacent-face grouping into larger islands, an explicit, honestly-stated scope limit of this simple packer.
