Coming from Rhino

Dino 8 deliberately speaks Rhino 8's command vocabulary, so almost everything you already know transfers directly. This page is an honest account of what is genuinely the same, what is different, and what Dino 8 does not do yet — drawn from the project's own self-audit (dino8-app/RHINO8_KILLER_AUDIT.md), not a marketing pitch.

What transfers directly

  • Command names and aliases. Box, b, Fillet, f, _/-/! macro prefixes, Enter-repeats-last-command, Esc-cancels — all identical.
  • Coordinate input. 10,5,0 absolute, @5,0 relative, 20<45 polar, bare distances along the cursor direction.
  • Viewport conventions. Four named viewports, right-drag orbit/pan, window vs. crossing selection, object snaps, ortho, the Gumball.
  • The .3dm format. Native read/write of layers, names, colors, user text, notes, named views, and units — files round-trip with real Rhino.
  • The core modeling vocabulary. NURBS curves/surfaces, B-rep solids, SubD, meshes, booleans, fillets/chamfers, transforms, and the command-line-driven workflow itself all work the way you expect.

What is different (in Dino 8's favor)

  • Price. Free, forever, no account, no license key, no telemetry, no subscription — verified by source inspection, not just a claim.
  • Undo can never desync. Every change snapshots the whole document, so Undo/Redo cannot get into the "silently stops working" state Rhino users occasionally hit. The tradeoff: undo is O(document size) instead of incremental, so it can feel slower on very large documents.
  • Command coverage as a checklist. All 1055 Rhino 8 catalog commands exist on the command line and in the Help panel (F1) — see the Command Reference for exactly which are fully implemented today.

What is different (real gaps you should know about)

These are the differences that will actually matter if you move a real workflow over. None of them are secret — each is called out, with the file/evidence behind it, in the project's self-audit.

Scripting: Lua only, no Python or .NET

Rhino ships RhinoScript, full Python 3, the RhinoCommon .NET SDK (C#/VB.NET/F#), and IronPython, with decades of tutorials and existing scripts. Dino 8 has an embedded Lua 5.4 scripting console and a from-scratch C plug-in ABI — real, but if your workflow leans on a Python or C# script library, it will not run as-is.

No construction history / associativity

Rhino's optional history lets many operations stay live-linked to their inputs. In Dino 8, edits (including GD&T annotations, tables, and Dino Flow bakes) are static/baked the moment they are created — moving a curve does not update anything downstream that was built from it.

Rendering: CPU path tracer, no GPU acceleration

Rhino Render / Raytraced mode is built on GPU-accelerated Cycles with denoising and a huge third-party ecosystem (V-Ray, KeyShot, Enscape, and more). Dino 8's path tracer is real and CPU-only, with a 48-material library and no GPU acceleration, denoiser, or third-party render plugin story.

Dino Flow vs. Grasshopper

Dino Flow is a genuine node-based visual scripting editor with real solving and baking, and it can drive plugin-registered nodes. It does not yet have Grasshopper's data-tree semantics (lists/graft/flatten), a solver/optimizer node family, or anything close to Grasshopper's 15+ years of third-party component ecosystem.

File format breadth

Dino 8 reads/writes .3dm, .obj, .stl, .step/.stp, .iges/.igs, .dxf, .pdf, .ply, and .svg. Rhino additionally reads/writes native DWG, SAT/ACIS, Parasolid (x_t/x_b), JT, FBX, glTF, and more — if your pipeline depends on one of those, keep Rhino (or another converter) in the loop for now.

No plugin ecosystem, no Grasshopper-plugin-equivalent marketplace

Dino 8 ships one first-party sample plugin ("HelloDino") and a real C ABI for building your own. Rhino has hundreds of commercial and free plugins built up over decades. This is a network-effect gap, not something either team can close by engineering alone.

Kernel robustness on hard, messy real-world geometry

Every Dino 8 command is verified against Dino 8's own scripted test corpus (about 950 checks) — simple, clean, deliberately-constructed geometry. Rhino's boolean/fillet/ intersection solvers have 30 years of fixes for the degenerate tangencies, huge tolerances, and messy imported topology that show up in real production files. If you regularly hit "hard" cases in Rhino, expect Dino 8 to be less forgiving on the same files today.

Smaller things worth knowing

  • Autocomplete is prefix-only (type Boo to see BooleanUnion/BooleanDifference/…), not the fuzzy match Rhino's command box supports.
  • No Rhino for iPad equivalent and no cloud/compute story (no Rhino Compute or ShapeDiver equivalent) — desktop only, on Windows, Linux, and macOS (including Windows-on-ARM).
  • English only — no localization infrastructure yet.
  • Installers are unsigned today, so Windows SmartScreen / macOS Gatekeeper will show a warning on first run. This is a trust/distribution gap, not a functional one.
  • Single-document, single-user — no worksessions-equivalent, no real-time multi-user co-editing (Rhino is also weak here, but has worksessions).
  • ToNURBS on a SubD is approximate, not exact smooth patches: the public OpenNURBS library Dino 8 builds against does not include Rhino's proprietary SubD-to-NURBS-patch conversion, so Dino 8 falls back to a densely subdivided mesh converted to a facetted B-rep. Converting an actual mesh object is exact.

Bottom line

If your workflow is core NURBS/SubD/mesh modeling, booleans, basic rendering, and Lua-friendly scripting, Dino 8's command-line muscle memory will feel immediately familiar and it costs nothing to try. If you depend on Python/RhinoCommon scripting, Grasshopper's plugin ecosystem, GPU-accelerated rendering, native DWG/Parasolid interop, or Rhino's 30 years of hardening against messy real-world files, keep Rhino around for those workflows — Dino 8 is not trying to hide that gap.
