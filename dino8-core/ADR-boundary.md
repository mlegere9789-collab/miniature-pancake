# ADR: the C/Rust boundary (Spike R1 result)

Status: spike complete; recommended for adoption. The decision belongs to the owner.
Date: 2026-11-14 (UTC). Plan references: Master Plan Revision 2, sections 5.1 (language policy),
5.2 (the C/Rust boundary) and 5.3 (retrofitting the operation log).
Branch: `w0-r1` (based on `cand2` at 1b690f52). Code: `dino8-core/ffi-probe/`.
Nothing outside `dino8-core/` was changed. The application's CMake files are untouched.

## 1. Verdict

The boundary works, is cheap, and its failure modes are known and contained.

- Gate, part 1 (one command round-trips through the log with overhead under 1 ms): **passed with a
  margin of about 5,700 times.** One append through the C ABI costs a mean of **0.175 microseconds**
  (median of 7 runs, range 0.142 to 0.200; the best single run was 0.113). The 99th percentile is
  1.5 microseconds and the 99.9th is 2.7 microseconds. The part that belongs to the boundary itself
  (handle lookup, panic guard, error record) is about 0.03 to 0.06 microseconds.
- Gate, part 2 (the full application test suite still passes): **not exercised here.** No file under
  `dino8-app/` or `dino8-kernel/` changed and this job was not allowed to build the app, so the suite
  has nothing to say yet. The job that wires the boundary into the application CMake must run it.
- A deliberate Rust panic does not unwind into C++: it comes back as a status code and a message,
  the same handle keeps working, and a panic that is NOT guarded makes the process abort rather than
  unwind (both proven, section 5).
- The C++ side runs under AddressSanitizer and UndefinedBehaviorSanitizer with zero findings
  (1,180 to 1,181 checks per run, both the static and the shared-library build). `cargo test` passes 39 tests,
  loom model checking passes (3 models, 293 + 46 + 4 interleavings, plus a negative control), and
  `cargo clippy` reports zero warnings.
- CMake drives Cargo through Corrosion v0.6.1 (fetched from GitHub by git). No fallback script was
  needed; a script path also exists and passes (`scripts/run_probe.sh`).
- The spike found and fixed one real defect that a mean would never show (section 6, F4) and found
  three rules the plan did not state: one Rust staticlib per program, callbacks must be declared
  `C-unwind`, and per-append `fdatasync` cannot meet 1 ms on this disk (F1, F3, F5).

## 3. Decision: the boundary rules

### 3.1 Shape of the ABI
1. Plain C ABI, generated by cbindgen into one committed header. No C++ type crosses it.
2. Coarse calls only: per command, per query, per batch (`d8_log_append_batch` appends many under one
   lock). Bulk data moves as arrays in caller buffers or, later, as content-addressed blobs.
3. Strings are UTF-8 and NUL-terminated at the boundary; blobs carry explicit lengths.
4. Sizes over a documented maximum are refused with `D8_ERR_LIMIT` before any slice is formed from
   the caller's pointer.
5. `d8_abi_version()` is compared with `D8_ABI_VERSION` from the header at start-up. Structs end with
   reserved fields; a layout change bumps the major version. Struct sizes and the offset of the
   error message are pinned by compile-time assertions on both sides (`ffi.rs` and
   `probe_test.cpp`, same numbers), so an accidental layout change fails the build.

### 3.2 Status codes and error records
- Every function returns an `int32_t` status (`D8_OK` = 0). Codes are `#define`d constants, not an
  enum, so a stale or foreign value cannot create an invalid enum in Rust.
- Every function takes an optional `D8Error*` (NULL is allowed). It carries the code, a detail value
  (OS error number, offending sequence number, or a callback's return value) and a message of up to
  239 UTF-8 bytes, NUL-terminated, truncated on a character boundary. The success path writes
  only four small fields. No thread-local "last error" exists, so there is nothing to race on.

### 3.3 Handles
- A handle is a 64-bit token in a one-field struct (`D8LogHandle`): 32-bit generation, 32-bit slot,
  zero never valid. The table holds `Arc` objects. Closing bumps the generation, so a closed,
  copied, forged or zero handle is answered with `D8_ERR_BAD_HANDLE`, never undefined behavior.
  A call that is in flight while another thread closes keeps its object alive until it returns and
  may see `D8_ERR_CLOSED`.
- `d8_log_close(D8LogHandle*)` zeroes the caller's variable, so closing twice is a no-op. The C++
  wrapper in `probe_test.cpp` (about 20 lines) closes in its destructor.
- Cost: 0.03 microseconds per call (a read lock and an atomic increment). This is the pattern for
  the "shared objects held by id in a handle table with reference counts" rule of plan 5.2; the
  probe implements it for the log only.

### 3.4 Ownership (each side frees only what it allocated)
1. Rust never hands memory to C++ to free. There is no `d8_free`. Results are values, static strings
   (`d8_status_name`, never freed) or bytes written into buffers the caller supplied.
2. C++ never frees, moves or resizes anything Rust allocated, never deletes a handle, and releases
   objects only through the matching `d8_*_close` or `release` call.
3. Inputs are borrowed for the duration of the call; the library copies what it keeps and keeps no
   pointer into caller memory after returning. Views lent to a callback are valid only until the
   callback returns.
4. Variable-size output uses a two-step protocol: when a buffer is too small the call returns
   `D8_ERR_BUFFER_TOO_SMALL`, writes nothing but the true sizes, and the caller retries with
   buffers of those sizes.
5. The error record belongs to the caller; Rust writes it and never keeps a pointer to it.
6. Memory the caller points at must not be changed by another thread during the call.
7. Both sides use the system allocator (the same `malloc`), so AddressSanitizer sees every
   allocation and finds a double or invalid free on either side. They still never free each other's
   memory: that rule is about ownership, not about the allocator.

### 3.5 Panics never cross
- Every `extern "C"` function runs its body inside `catch_unwind` (`guarded()` in `ffi.rs`) and turns a
  panic into `D8_ERR_PANIC` plus the panic message. Destructors of Rust locals run during the
  unwind (counted in the test).
- The functions are plain `extern "C"`, not `C-unwind`. If a panic ever escaped a function that lacks
  the guard, the Rust runtime aborts the process; it does not unwind into C++ (proven in a forked
  child: signal 6).
- A panic while the log's lock is held poisons that log: it answers `D8_ERR_POISONED`, can still be
  closed, and other logs are unaffected. Failing safe beats exposing half-updated state in a
  write-ahead log.
- The release profile must keep `panic = "unwind"` (it is set explicitly). With `panic = "abort"`
  every panic would end the process instead of becoming a status code.
- The default panic message still goes to stderr; the app should route it to its log.

### 3.6 C++ exceptions and callbacks (Rust calling C++)
- Callback function types are declared `extern "C-unwind"` in Rust. A C++ exception that escapes such a
  callback is then caught by the guard, and the Rust runtime aborts with "Rust cannot catch foreign
  exceptions" (proven: forked child dies with signal 6). With a plain `extern "C"` callback type the
  same escape was observed to skip the Rust frames entirely and land in an outer C++ handler,
  which is undefined behavior that would leave Rust locks and state half-released (F1).
- Rule for C++: every function passed to the library is a thin wrapper whose body is
  `try { ... } catch (...) { return <error code>; }`. The abort is only the last line of defense.
- The library never calls a callback while holding one of its locks (`d8_log_visit` copies a batch of
  records out, releases the lock, then calls back). A callback may therefore call back into the
  library, which the test does.
- Rust scheduler threads may call kernel functions only through such callbacks, and only for kernel
  functions declared thread-safe (Spike C). The probe has no kernel and cannot say more.

### 3.7 Threads
All log functions are thread-safe on one handle. Appends are serialized by one mutex; `d8_log_len`
is a lock-free atomic read. 4 threads appending to one log reach about 6 million appends per second
in aggregate.

## 4. Measurements

Machine: 4-vCPU Intel Xeon 2.30 GHz VM shared with about 20 other agents (load average 6 to 13
during these runs), Ubuntu 24.04, GCC 13.3, rustc/cargo 1.97.0, CMake 3.28.3, Ninja. The program was
built `RelWithDebInfo` (-O2) and the crate in the `release` profile (opt-level 3, thin LTO). The
record is 48-byte header + 64-byte parameters + 2 input ids + 1 output id = 160 bytes (168 in the
file). Numbers are microseconds per call; "7 runs" means seven complete runs of the program, shown as
median [minimum to maximum]. A loaded machine makes every figure noisier and slower than quiet
hardware would give; the probe is cheap to rerun (`ctest`) on the owner's machine.

### 4.1 Per-call cost, 1,000,000 operations, static link (7 runs)

| What | Microseconds per call |
|---|---|
| Bare C-to-Rust call, no guard | 0.0005 [0.0005 to 0.0013] |
| Guarded call (panic catch + error record), does nothing | 0.0011 [0.0008 to 0.0027] |
| Handle lookup + lock-free length | 0.0315 [0.027 to 0.038] |
| **`d8_log_append`, 1M operations, mean** | **0.175 [0.142 to 0.200]** |
| Same append called natively from Rust, no boundary (5 runs, different minutes) | 0.119 [0.099 to 0.128] |
| `d8_log_append_batch`, 1000 per call, per operation | 0.118 [0.107 to 0.187] |
| `d8_log_read` back, sequential, per record | 0.079 [0.067 to 0.193] |
| 4 threads, one shared log, per append (aggregate) | 0.165 [0.148 to 0.288] |
| Dynamic link (cdylib), `d8_log_append` mean (3 runs) | 0.152 [0.119 to 0.195] |

Reading it: the bare call costs half a nanosecond and the guard one nanosecond, so the panic safety
net is free. The boundary-specific cost is the handle lookup, about 0.03 microseconds. The rest of
the 0.14 to 0.20 is the append itself (copying 160 bytes under a mutex), which a native Rust caller
pays too. The 1,000,000 records occupy 152.6 MiB in memory (160 bytes each) in 39 segments.

### 4.2 Tail latency (timed pass, every one of the 1,000,000 calls timed, 7 runs)

| Statistic | Microseconds |
|---|---|
| median (p50) | 0.079 [0.075 to 0.079] |
| p99 | 1.48 [1.40 to 1.61] |
| p99.9 (the gate statistic with the mean) | 2.71 [2.52 to 2.99] |
| worst single call | 4,049 to 19,011 (median 7,945) |
| calls over 1 ms, per 1,000,000 | 14 [4 to 38] |

The p99 is the page fault of the first touch of fresh memory (one per 25 appends). The worst calls
are not the library: 5,000,000 timed calls of an EMPTY guarded function show the same thing in
every run (worst call 4,043 to 7,856, median 4,178; over 1 ms: median 13 per run), and so does a
library-free loop that allocates 64 KiB and touches it (about 0.5 percent of iterations over 1 ms,
p99.9 about 4.1 ms, measured in a scratch program, not committed). Four milliseconds is the
scheduler time slice on this oversubscribed VM. The library's own growth paths cost, per occurrence:
a new 4 MiB segment 5.4 microseconds (median; worst 179), a new 8192-entry index page 36
microseconds (median). The gate is therefore judged on the mean and p99.9; the worst case on this
machine is dominated by the host. Re-measure on owner hardware before quoting a worst case. The
host can also stall a whole run: one of the 12 release runs (load average 12) had a bulk mean of
1.2 microseconds because the process was descheduled for about a second, while its timed-pass
percentiles (p50 0.080, p99 1.46, p99.9 2.47) matched the others; that run is not in the table.

### 4.3 Durability modes (file-backed log)

| Mode | Microseconds per append | Survives |
|---|---|---|
| In memory only | 0.175 | nothing |
| File, buffered (64 KiB buffer, flushed on `d8_log_sync` and close) | 0.66 [0.61 to 0.85] | clean exit |
| File, write-through (one `write` per append) | 1.05 [0.91 to 1.14] | process crash |
| File, `fdatasync` per append | 900 to 3,795 (5 runs); 2,300 to 5,778 in two earlier runs | power failure |
| One `fdatasync` after 200,000 buffered appends (32 MiB) | 51 to 124 ms in total | power failure |

Per-append `fdatasync` on this VM's disk costs 1 to 6 ms and cannot meet a 1 ms target on any
design; that is the disk, not the boundary. Recommended policy for plan 5.3: append write-through
(1 microsecond, survives an application crash, which is the crash-recovery case in the plan), and
make power-loss durability a group commit: `d8_log_sync` at command-batch boundaries or on a timer.
The plan's target "log append under 1 ms" should be read as write-through append.

### 4.4 Build and size
- CMake configure 1.9 s, cold build 6.8 s (cargo inside it 1.6 s), build directory 89 MB (93 MB with
  sanitizers). The crate has no dependencies, so this is the floor; real crates add compile time.
- A stripped C++ hello program is 14 KB; the same with the Rust log linked in (`--gc-sections`) is
  349 KB. The unstripped staticlib is 23 MB and the cdylib 4.7 MB (both with line-level debug info).
- loom adds about 32 s of one-time compile (it is only built under `--cfg loom`).

## 6. Findings that changed the design

- **F1. A C++ exception escaping a callback.** With the callback type declared plain `extern "C"` (the
  first version) a forked child that let an exception escape did not abort: it unwound past the Rust
  frames into an outer C++ handler and kept running. That is undefined behavior and would leave
  Rust state half-released. Declaring the callback type `extern "C-unwind"` makes the same mistake a
  clean abort. Both layers are now required: C++ wrappers catch everything, Rust declares `C-unwind`.
- **F2. Unguarded panic.** A Rust `extern "C"` function with no guard aborts the process (signal 6);
  it does not unwind into C++. The guard exists to turn that into an error code.
- **F3. Two Rust staticlibs in one program do not link.** Each carries its own copy of the Rust
  standard library. Linking a second trivial Rust staticlib with the probe gave 208 "multiple
  definition" errors with GNU ld and 20 with lld (lld stops at 20). Rule: exactly ONE Rust staticlib
  per final binary: a single facade crate that depends on the component crates and exports all
  `extern "C"` functions. (Dynamic libraries keep separate copies and were not tested.)
- **F4. Latency spikes from vector doubling.** The first 1M-append run showed three slow appends at
  sequence numbers 131,072, 262,144 and 524,288 (0.5, 1.2 and 2.1 ms): the undo stack and index were
  ordinary vectors that copy everything when they double. Replaced by a paged sequence whose pages
  never move (`paged.rs`); the spikes are gone (the slow calls that remain sit at random positions
  and match the empty-call noise). Any hot-path container in the real core needs the same
  treatment, and the timed pass in the probe is how to catch it.
- **F5. Durability and the 1 ms target.** See 4.3.
- **F6. ThreadSanitizer cannot see inside an uninstrumented Rust library.** Without suppressions TSan
  reports one data race at `realloc` inside Rust's `Vec`, between two threads that are in fact
  serialized by the Rust mutex. The suppression file hides Rust frames, so TSan checks the C++ side
  only. The Rust side is covered by loom and the type system (`Log` must be `Send + Sync` to sit in
  the global table). A Rust-side TSan needs a nightly toolchain (`-Zsanitizer=thread -Zbuild-std`).
- **F7. Header hygiene.** cbindgen exports every `pub const` of the crate, which put names like
  `HEADER_LEN` into the C namespace; ABI constants now carry a `D8_` prefix and internal ones are
  marked `cbindgen:ignore`. `D8_ERROR_INIT` is `{}` in C++ because `{ 0 }` triggers
  `-Wmissing-field-initializers` under `-Wextra`. The drift check caught a stale header once.
- **F8. Clippy and the MSRV.** Clippy hides newer lints when `rust-version` is old. The code was
  checked with the field removed, which exposed three; they are fixed, so zero warnings holds on a
  current toolchain too.
- **F9. Network.** CMake `FetchContent` must use `GIT_REPOSITORY`; the GitHub archive tarball URL is
  refused (HTTP 403) by this environment's network policy while `git clone` works.

## 7. Build integration steps for the real app CMake (NOT applied in this job)

1. **One Rust staticlib.** Create the facade crate (for example `dino8-core/dino8-core-ffi/`) with
   `crate-type = ["staticlib"]` (add `"cdylib"` only for the sync server or plug-in builds). Component
   crates (log, store, scheduler) are ordinary `rlib` path dependencies of it. Only the facade exports
   `extern "C"` functions. Keep `[profile.release] panic = "unwind"`. Add `rust-toolchain.toml` pinning
   the stable version CI uses. Give every Rust crate `#![deny(unsafe_op_in_unsafe_fn)]` and confine
   `unsafe` to the facade, as the probe does.
2. **Corrosion.** In the top-level `CMakeLists.txt`, before the app target (the probe's tested form):
   ```cmake
   include(FetchContent)
   FetchContent_Declare(Corrosion
     GIT_REPOSITORY https://github.com/corrosion-rs/corrosion.git
     GIT_TAG v0.6.1 GIT_SHALLOW TRUE)       # pin the commit hash in the real file
   FetchContent_MakeAvailable(Corrosion)
   corrosion_import_crate(MANIFEST_PATH ${CMAKE_SOURCE_DIR}/dino8-core/Cargo.toml)
   target_link_libraries(dino8_app PRIVATE dino8_core_ffi)   # hypothetical name: the target is the [lib] name
   target_include_directories(dino8_app PRIVATE ${CMAKE_SOURCE_DIR}/dino8-core/dino8-core-ffi/include)
   ```
   Corrosion v0.6.1 needs CMake 3.22 or newer (its own `cmake_minimum_required`) and maps CMake build types to Cargo profiles (Debug to
   `dev`, every other type to `release`; seen in the probe's build log). For an offline or
   locked-down CI set `-DFETCHCONTENT_SOURCE_DIR_CORROSION=<vendored checkout>`. Documented but untested
   here, to try in the integration job: `CRATES` and `CRATE_TYPES staticlib` so Cargo does not also build the
   cdylib and rlib on every build (the probe builds all three).
3. **Header.** Commit the generated header. Add a CTest entry that runs
   `scripts/gen_header.sh --check` (the probe does) and make CI fail when it is out of date.
   Install cbindgen in CI with `cargo install cbindgen --locked` (0.29.4 was used).
4. **System libraries.** Corrosion read `-lgcc_s -lutil -lrt -lpthread -lm -ldl -lc` from
   `rustc --print native-static-libs` and added them to the link; nothing to maintain by hand on
   Linux. macOS and Windows (MSVC) need the same mechanism and are untested.
5. **C++ conventions.** Include the header from a thin wrapper namespace, not directly from command
   code. Provide (a) an RAII class per handle type that closes in its destructor, (b) a
   `catch (...)` wrapper template for every callback given to Rust, (c) a status-to-exception or
   status-to-result adapter. Check `d8_abi_version()` at start-up.
6. **Sanitizers.** Add `-fsanitize=address,undefined` (and a separate `thread` job) to C++ only; link
   with the same flags. Run the existing app suite and the boundary probe in that configuration.
   ASan replaces `malloc` for the whole process, so double or invalid frees are caught on both sides.
7. **CI jobs** (each exists in the probe and runs in seconds): `cargo fmt --check`;
   `cargo clippy --all-targets -- -D warnings` (standard and `--cfg loom`); `cargo test`;
   loom (`RUSTFLAGS="--cfg loom"`); CMake build plus `ctest` in release and in ASan+UBSan; TSan on
   C++ with `scripts/tsan.supp`; header drift check. Weekly on nightly (not run in this spike): Miri
   on the pure-Rust crates and a Rust-instrumented TSan.
8. **Command bus (plan 5.3, Stage 1).** The dispatcher fills one `D8OpRecord` per command and calls
   `d8_log_append`; cost per command is about 0.2 microseconds plus serializing the parameters, which
   will dominate and was not measured. Use `d8_log_append_batch` for macros and imports.
9. **Remove or gate the probe-only functions** (`d8_probe_*`) behind a Cargo feature before
   shipping; keep them in the test build.
10. **Run the full app test suite** in the new configuration. This is gate part 2 and is open.

## 8. Not proven, and risks

- Gate part 2 (app suite) was not run; see section 1.
- The probe has no kernel behind it. Thread-safety of kernel functions called from Rust threads is
  Spike C's question. Callbacks were tested with a C++ function only.
- Windows and macOS builds were not tried. The Rust code uses only the standard library and the
  C++ test guards its POSIX-only parts (`fork`, `truncate`), but that is untested.
- Miri and a Rust-instrumented TSan were not run: they need the nightly toolchain (an estimated 600 to 800 MB on a
  disk with 5 GB free for everyone). loom, ASan/UBSan on the C++ side, and the type system are the
  evidence for the Rust side's soundness here.
- The log is single-process. Two processes appending to one file would corrupt it; the real design
  needs a file lock.
- Handles are checked for staleness but the table is a global lock; 0.03 microseconds per call is
  fine for coarse calls and would not be for per-vertex calls, which the rules forbid.
- Worst-case latency was measured on a heavily shared machine and is dominated by the host (4.2).
- Record parameters are opaque bytes here. Their schema is plan Stage 2.
- The ABI is a design for these functions; growing it to roughly 1,070 commands' worth of typed
  parameters is not a boundary question, but it is the largest remaining piece of work.
